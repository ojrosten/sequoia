      10              : /** @file
      11              :     @brief Abstractions pertaining to vector spaces, affine spaces and their
      12              :            generalizations.
      13              : 
      14              :     Representing abstract algebraic structures in C++ presents an interesting
      15              :     challenge. At root, the fundamental abstraction is a set; indeed, a vector
      16              :     space is nothing but a set with some additional structure defined. However,
      17              :     sets of objects are not straightforward to represent, in general, in C++.
      18              : 
      19              :     Consider the real numbers. In C++ we can give a name to the set by using
      20              :     the type system.
      21              : 
      22              :     @code
      23              :     struct reals {};
      24              :     @endcode
      25              : 
      26              :     But what of the elements of `reals`? Here we run into an immediate
      27              :     difficulty. We would like to associate them with the values of a type. But
      28              :     to truly do so we require a type with an infinite number of values (and
      29              :     uncountably so, in this case). Therefore, when seeking representations,
      30              :     particularly of infinite sets, we are generally reduced to approximations.
      31              : 
      32              :     However, at least in so far as the set underpinning a particular vector
      33              :     space goes, it turns out that, for our purposes, we need go no further than
      34              :     naming it. As we will explain momentarily, this is because when dealing
      35              :     with vector spaces in practice, we are almost always interested in the
      36              :     _coordinates_ of a vector with respect to a particular basis and not the
      37              :     abstract entities comprising the elements of the underlying set.
      38              : 
      39              :     Before discussing coordinate systems, it is helpful to be more precise
      40              :     about the fundamental definition of a vector space. The axioms governing
      41              :     addition pertain just to the elements of the underlying set and amount to
      42              :     stating that a vector space is an abelian group under addition. Thus,
      43              :     vector addition is associative and commutative, there is an identity
      44              :     element and every element admits an inverse.
      45              : 
      46              :     However, the remaining properties of a vector space require not just the
      47              :     underlying set, V, but also a field, F. As such, we speak of a vector space
      48              :     over a field. Canonical examples of a field include the rationals and the
      49              :     reals. Concretely, a field is a set admitting addition and multiplication
      50              :     such that:
      51              :     -# Both operations are associative and commutative, with identity elements
      52              :        0 and 1 respectively;
      53              : 
      54              :     -# Multiplication distributes over addition, i.e. \f$ a(b+c) = ab + ac \f$,
      55              :        where a, b and c are all elements of the field;
      56              : 
      57              :     -# Every element has an additive inverse;
      58              : 
      59              :     -# Every non-zero element has a multiplicative inverse.
      60              : 
      61              :     A vector space is equipped with a scalar multiplication, by which any
      62              :     element of V may be multiplied by any element of F to give an element of V.
      63              :     Writing a and b for elements of F, and \f$ \vc{u} \f$ and \f$ \vc{v} \f$
      64              :     for elements of V, scalar multiplication is subject to four further axioms:
      65              :     -# It distributes over addition in the vector space, i.e.
      66              :        \f$ a(\vc{u} + \vc{v}) = a\vc{u} + a\vc{v} \f$;
      67              : 
      68              :     -# It distributes over addition in the field, i.e.
      69              :        \f$ (a + b)\vc{v} = a\vc{v} + b\vc{v} \f$;
      70              : 
      71              :     -# It is compatible with multiplication in the field, i.e.
      72              :        \f$ a(b\vc{v}) = (ab)\vc{v} \f$;
      73              : 
      74              :     -# The multiplicative identity of the field leaves vectors unchanged, i.e.
      75              :        \f$ 1\vc{v} = \vc{v} \f$.
      76              : 
      77              :     It is interesting to observe why the final axiom is necessary: without it,
      78              :     setting \f$ a\vc{v} = \vc{0} \f$ for every a and \f$ \vc{v} \f$ would
      79              :     satisfy the first three.
      80              : 
      81              :     A basis of a vector space is a set of vectors which is linearly independent
      82              :     and spans the space. Spanning means that any vector can be built from the
      83              :     set using scalar multiplication and addition; linear independence means
      84              :     that no member of the set can be built from the others. There are theorems
      85              :     that:
      86              :     -# Every vector space admits at least one basis;
      87              : 
      88              :     -# All bases of a given space have the same size; this common value is the
      89              :        dimension of the vector space, d;
      90              : 
      91              :     -# In a space of dimension d, any d linearly independent vectors form a
      92              :        basis.
      93              : 
      94              :     Choosing an ordering of a finite basis, let its elements be denoted
      95              :     \f$ \vc{b}_0, \ldots, \vc{b}_{d-1} \f$. Any vector in the space may be
      96              :     written as a linear combination:
      97              : 
      98              :     \f[
      99              :       \vc{v} = a_0 \vc{b}_0 + \ldots + a_{d-1} \vc{b}_{d-1},
     100              :     \f]
     101              : 
     102              :     where the \f$ a_i \f$ are valued in the field, F. The tuple of these
     103              :     values, \f$ [a_0, \ldots, a_{d-1}] \f$, is none other than the coordinates
     104              :     of \f$ \vc{v} \f$ with respect to this particular basis. The
     105              :     \f$ [a_0, \ldots, a_{d-1}] \f$ are often informally referred to as a
     106              :     vector. However strictly speaking this risks an abuse of terminology since
     107              :     it may conflate two distinct concepts: an actual vector which is an element
     108              :     of the set which forms the vector space, and a representation of this
     109              :     vector via the coordinates with respect to a particular basis. This
     110              :     distinction can be further reinforced by pointing out that two observers
     111              :     who agree they are talking about the same vector (i.e. set element) will
     112              :     nevertheless disagree on the coordinates if they are using different bases
     113              :     - as they are entirely entitled to do! To further add to the confusion, the
     114              :     coordinates may be referred to as a coordinate vector which is perhaps
     115              :     unfortunate. (To add to the fun, in the case of \f$ \bb{R}^d \f$, a tuple
     116              :     of values \f$ (v(0), \ldots, v(d-1)) \f$ can have a different
     117              :     interpretation, which we shall gloss over for now but return to in
     118              :     \ref Basis "Basis".)
     119              : 
     120              :     Regardless, from the perspective of performing actual calculations, the
     121              :     coordinates are key. A crucial point to make is that, when dealing with the
     122              :     coordinates, the underlying elements of the set, V, make no explicit
     123              :     appearance. This is a manifestation of the fact that a choice of basis
     124              :     supplies an isomorphism from V onto \f$ F^d \f$, so that calculations may
     125              :     be performed entirely on the coordinates. Put another way, two vector
     126              :     spaces over the same field and of the same dimension are isomorphic. These
     127              :     considerations are incredibly helpful since, for many practical purposes,
     128              :     we need not represent the underlying set beyond, at most, perhaps giving it
     129              :     a name. For example, consider the vector space formed by functions which
     130              :     map some finite set into a field: the question of how to represent the
     131              :     elements of this vector space in C++ is completely circumvented.
     132              : 
     133              :     However, that is not to say that subtleties of imperfect representations of
     134              :     mathematical abstractions are entirely avoided; indeed, quite the contrary!
     135              :     The coordinates are valued in a field and so at this stage we must deal
     136              :     with the fact that C++ types such as float and double model the real
     137              :     numbers imperfectly. Nevertheless, the burden has been shifted from
     138              :     attempting to represent things in C++ that may be completely infeasible to
     139              :     things which can be done to reasonable approximation. Generally we will
     140              :     speak of e.g. the doubles \ref AlgebraicTraits "weakly" representing the
     141              :     reals.
     142              : 
     143              :     Vector spaces are just one of the things treated in the code that follows.
     144              :     There are several important generalizations. First, there are affine
     145              :     spaces, which comprise a set, A, together with a vector space, V, whose
     146              :     additive group acts freely and transitively on A. Intuitively, we can start
     147              :     at any point in A and translate to any other point by adding the
     148              :     appropriate vector. \anchor FreeTransitiveAction There are three separate
     149              :     things being asserted:
     150              :     -# That V acts at all: adding any vector in V to any point of A gives a
     151              :        point of A;
     152              : 
     153              :     -# That it acts transitively: for any two points of A there is at least one
     154              :        vector which translates from the first to the second;
     155              : 
     156              :     -# That it acts freely: there is at most one such vector or, equivalently,
     157              :        the only vector which translates a point of A to itself is the zero
     158              :        vector.
     159              : 
     160              :     The last two together say that the vector translating between any two
     161              :     points is unique.
     162              : 
     163              :     A nice example of an affine space is Euclidean space. Two observers in this
     164              :     space, Alice and Bob, are entirely entitled to define their location as the
     165              :     origin. Neither is more right than the other since this space has no
     166              :     distinguished origin. Alice and Bob will, in general, disagree about the
     167              :     coordinates of points in the space. However, they will agree on the vector
     168              :     which translates from one point to another (though if they compare vector
     169              :     coordinates, they may have to contend with using different bases on the
     170              :     vector space!).
     171              : 
     172              :     An affine space is sometimes described as a vector space which has
     173              :     forgotten its origin. Indeed, a vector space is an affine space over
     174              :     itself. This is interesting in terms of representing these concepts in C++.
     175              :     Since a vector space is a special case of an affine space, this suggests
     176              :     that an affine space concept is more fundamental, with the vector space
     177              :     being a refinement. However, a vector space is part of the definition of an
     178              :     affine space (a set and a vector space, satisfying certain conditions) and
     179              :     so it is this that will be reflected by the concepts defined below: the
     180              :     affine space concept depends on the vector_space concept, and not
     181              :     vice-versa.
     182              : 
     183              :     It will be useful for our purposes to generalize affine spaces. To start,
     184              :     consider taking a convex subset, C, of an affine space. We may translate
     185              :     from any point in C to any other by adding the appropriate vector from V.
     186              :     However, there are elements of V which, when added to a point in C, will
     187              :     take us outside of C and into the broader affine space of which it is a
     188              :     part. Yet we do not want to define such a space via an embedding in a
     189              :     bigger one; we would like to characterize it in its own right.
     190              : 
     191              :     The way forward is to relax the requirement that the action of V be defined
     192              :     for every combination of point and vector. Of the three properties relating
     193              :     to a \ref FreeTransitiveAction "free and transitive action", the last two
     194              :     survive: for any two points of C there is still a unique vector which
     195              :     translates from the first to the second. What is lost is the first, that
     196              :     any point and any vector may be combined to give a point. Retaining
     197              :     uniqueness but not totality leaves us with:
     198              :     -# A set, A, together with a vector space, V;
     199              : 
     200              :     -# The difference of any two points of A, which is an element of V;
     201              : 
     202              :     -# The sum of a point, p, of A and a vector, \f$ \vc{v} \f$, which is
     203              :        defined precisely when \f$ \vc{v} \f$ is the difference of some point of
     204              :        A and p.
     205              : 
     206              :     The last of these is what is meant by saying that V acts partially on A.
     207              :     Here partial carries its usual mathematical sense of "not necessarily
     208              :     defined everywhere", much as a partial order need not order every pair of
     209              :     elements. A total action is therefore a partial action, and affine spaces
     210              :     are recovered as precisely those cases for which the sum is defined for
     211              :     every point and every vector.
     212              : 
     213              :     The mathematical structure we have arrived at is a partial torsor over a
     214              :     vector space. There are two important points to bear in mind:
     215              :     -# The construction does not require embedding in a bigger space: there is
     216              :        no need to consider the set, A, as a subset of anything else.
     217              : 
     218              :     -# While convexity is a useful property of some spaces, and provided a hook
     219              :        into this discussion, it is not a requirement placed on our partial
     220              :        torsor: our construction is more general and flexible than that.
     221              : 
     222              :     The notion of a partial action is a standard one, and comes with a useful
     223              :     theorem: every partial action of a group on a set can be considered to
     224              :     arise from restricting a total action to a subset. While we have
     225              :     deliberately avoided explicitly embedding the torsor into an affine space
     226              :     as part of our construction, this option is retrospectively available, for
     227              :     free, providing useful intuition.
     228              : 
     229              :     There is a second generalization that it will be profitable to explore,
     230              :     namely relaxing a vector space's field to a ring. The resulting
     231              :     construction is called a module, which is a generalization of a vector
     232              :     space. Our motivation for this is that the integers form a commutative ring
     233              :     and not a field, since integers do not, in general, have multiplicative
     234              :     inverses valued within the integers. Rather than attempting to deal with
     235              :     modules in full generality, we restrict our attention to what may be the
     236              :     most useful, practical cases in the context of C++: free modules over
     237              :     commutative rings. Free modules are those which admit a basis.
     238              : 
     239              :     Combining the two generalizations brings us to the most primitive
     240              :     abstraction with which the code deals: the partial M-torsor. A torsor is a
     241              :     set upon which a group acts
     242              :     \ref FreeTransitiveAction "freely and transitively"; allowing partiality
     243              :     gives the structure described above. The 'M' indicates that the group in
     244              :     question is the additive group of a free module, M, rather than of a vector
     245              :     space. In the same spirit, it is useful to delineate affine spaces over a
     246              :     field from those over a free module; we refer to the latter as M-affine
     247              :     spaces. This is a mild extension of the usual terminology, in which an
     248              :     affine space is over a vector space.
     249              : 
     250              :     Convexity remains a useful refinement, and appears as one in the code: a
     251              :     convex space is a partial M-torsor for which, whenever two points belong
     252              :     to the space, so do the points lying between them. Intuitively, this
     253              :     corresponds to being able to linearly interpolate (lerp): given two points
     254              :     p and q
     255              :     and a parameter t in the range [0, 1], we may construct intermediate
     256              :     points, r, using the recipe
     257              :     \f[
     258              :         r = (1 - t)p + t q.
     259              :     \f]
     260              :     However, any notion that r is between p and q requires the ring to
     261              :     which t belongs
     262              :     -# To be ordered;
     263              : 
     264              :     -# To admit values between zero and one other than these two. Indeed, if
     265              :        t is an element of the integers, the above formula degenerates to only
     266              :        ever producing p or q.
     267              : 
     268              :     While there are useful generalizations of convexity that apply when the
     269              :     second condition is not satisfied, we do not pursue them. However, there
     270              :     is nothing to prohibit appropriate concepts being added in the future.
     271              :     Therefore, we define convex spaces to be refinements of a partial
     272              :     M-torsor for which the commutative ring is an ordered field. (Note: this
     273              :     rules out the case of the dyadic rationals which satisfy both
     274              :     conditions above; if a use case for these ever arises the framework can
     275              :     be enhanced.)
     276              : 
     277              :     The relationships between the structures introduced above form a DAG, in
     278              :     which refinements appear below that which they refine:
     279              :     @verbatim
     280              :                 partial M-torsor
     281              :                /                \
     282              :      (M-convex space)       M-affine space
     283              :             |                 /        \
     284              :        convex space   affine space   free module
     285              :                              \          /
     286              :                              vector space
     287              :     @endverbatim
     288              :     The bracketed entry marks where an M-convex space would sit, were the
     289              :     generalizations of convexity alluded to above pursued. Note also that
     290              :     affine spaces are not, in general, convex spaces: the latter require an
     291              :     ordered field, whereas there is nothing untoward about an affine space
     292              :     over the complex numbers.
     293              : 
     294              :     The diagram orders the structures by refinement alone, and the order in
     295              :     which they must be defined runs the other way: a partial M-torsor is a
     296              :     set together with a free module acting on it, so free modules are prior
     297              :     to everything above them here, just as vector spaces are prior to affine
     298              :     spaces. There is no circularity: free modules and vector spaces appear as
     299              :     nodes at all only because a free module is an M-affine space over itself.
     300              : 
     301              :     Nor are the edges all of a kind. Most impose a condition: that the action
     302              :     is total, or that the ring is a field or an ordered field. The two edges
     303              :     descending into a free module and into a vector space are not of this
     304              :     sort: every M-affine space can be turned into a free module by nominating
     305              :     any one of its points as the origin and transporting the structure there.
     306              :     What separates a free module from an M-affine space is therefore not a
     307              :     condition but a choice. The distinction manifests if the diagram is read
     308              :     upwards. A vector space regarded as a free module is the very same object,
     309              :     with a requirement merely no longer in force; regarded as an affine space,
     310              :     it has given up its origin and with it the ability to add one point to
     311              :     another. That is the sense in which an affine space is a vector space
     312              :     which has forgotten its origin.
     313              : 
     314              :     We now turn to the important question of how to deal with translations
     315              :     which would take us outside the underlying space. Up to this point of our
     316              :     rather abstract analysis, we have simply declared that such operations do
     317              :     not exist. But this is not a luxury we have in the world of C++; moreover,
     318              :     there may be physical or mathematical reasons to introduce additional
     319              :     behaviour. For example, consider the convex space comprising a
     320              :     one-dimensional interval and the associated free module of translations.
     321              :     Perhaps we represent the interval by all the `double`s in the range [0.0,
     322              :     1.0]. What happens if we start at the point 0.5 and use `operator+` to
     323              :     perform the translation 0.5 + 1.0? We must decide, since there is no way
     324              :     for us to stop clients from writing such an expression. Broadly speaking,
     325              :     there are four approaches:
     326              :     -# Treat this as undefined behaviour;
     327              : 
     328              :     -# Treat the behaviour as exceptional;
     329              : 
     330              :     -# Adjoin an absorbing state to the space;
     331              : 
     332              :     -# Recognize that there is additional physical or mathematical structure
     333              :        which remaps the answer back into the space.
     334              : 
     335              :     Let us expand on these in turn.
     336              : 
     337              :     @par Undefined behaviour
     338              :     In C++ we cannot literally restrict the domain of a function such as
     339              :     operator+, but we can furnish it with a precondition. The behaviour when
     340              :     called out of contract is undefined; not quite in the mathematical sense,
     341              :     but in a sense which maps rather well onto our intuition. Since C++26, this
     342              :     precondition may be expressible in code.
     343              : 
     344              :     @par Exceptional behaviour
     345              :     Two things are in play here - the mathematics and its C++ representation -
     346              :     and it is worth being clear about which is which. A partial function is the
     347              :     same thing as a total function whose codomain has been enlarged by a single
     348              :     extra element, \f$ \bot \f$, signalling that there is no result. To widen
     349              :     the codomain in this sense is not to change the mathematics but to restate
     350              :     it: the space is untouched, and \f$ \bot \f$ is emphatically not a point of
     351              :     it, so nothing can be translated from it. Gratifyingly, C++ can transcribe
     352              :     the mathematics exactly, by having `operator+` return `std::expected`;
     353              :     specifying it to throw expresses the same thing through a different
     354              :     mechanism. Note, though, that `operator+=` cannot return anything of the
     355              :     sort, since it must write its result back into a point: either it throws,
     356              :     or the extra element is admitted into the space itself, which brings us to
     357              :     the next option.
     358              : 
     359              :     @par Absorbing states
     360              :     We can supplement the set underpinning the space in question with an
     361              :     absorbing state. In C++, an example would be to use NaN. While adding a
     362              :     displacement to a point is now always mathematically defined, the group law
     363              :     is broken whenever this state is involved. Consider our previous example
     364              :     where 0.5 + 1.0 goes outside the space. As such, suppose we return NaN.
     365              :     This is what absorbing means: subtracting 1.0 still leaves us with NaN and
     366              :     does not take us back to 0.5. Consequently, translating by 1.0 and then by
     367              :     -1.0 no longer agrees with translating by their sum, 0.0, which does
     368              :     nothing at all; and it is precisely such agreement that an action of a
     369              :     group demands. What makes this a genuine change to the space, rather than a
     370              :     way of reporting an error, is that the absorbing state is a value like any
     371              :     other: it may be stored, passed on and translated from.
     372              : 
     373              :     @par Remapping
     374              :     Here there are many options, of which we single out three particularly
     375              :     natural ones, analogous to the wrapping modes which graphics hardware
     376              :     offers for texture coordinates.
     377              : 
     378              :     -# Clamp to the boundary. Again every sum is defined and again the group
     379              :        law fails: in the interval [0.0, 1.0], translating 0.5 by 1.0 and then
     380              :        by -1.0 arrives at 0.0 rather than at 0.5. Note that this option alone
     381              :        requires the embedding in a larger space which we have avoided when not
     382              :        strictly necessary, since the point outside the set must be formed
     383              :        before it can be clamped back. A variant selects the first point at
     384              :        which the ray from the starting point strikes the boundary.
     385              : 
     386              :     -# Remap periodically, identifying points which differ by an element of
     387              :        some lattice, L. This changes the nature of the space. The action of M
     388              :        remains total and transitive but no longer free, since every element of
     389              :        L translates every point to itself. What we have is a torsor over the
     390              :        quotient M/L.
     391              : 
     392              :     -# Remap anti-periodically, so that the coordinate reverses direction each
     393              :        time it would leave the set. This also changes the space, but more
     394              :        drastically: the group which acts now contains reflections as well as
     395              :        translations, and the translations of M do not survive the quotient.
     396              :        Taking the unit interval again, translating 0.9 by 0.2 twice gives 0.9,
     397              :        whereas translating once by 0.4 gives 0.7. The interval is best regarded
     398              :        as a fundamental domain for this larger group rather than as a set on
     399              :        which M acts.
     400              : 
     401              :     Of the six possibilities canvassed, only the first two - which between them
     402              :     leave the mathematics as the partial torsor - keep M acting on the set by
     403              :     translations. The absorbing state and clamping retain totality at the
     404              :     expense of the group law, while the two periodic remappings retain the
     405              :     group law by changing the space and, with it, the group which acts. This is
     406              :     why it is the partial torsor, rather than any of the alternatives, which
     407              :     generalizes an affine space.
     408              : 
     409              :     The final introductory issue to address is the question of why to bother
     410              :     modelling concepts such as vector spaces in the abstract sense if it is
     411              :     their coordinates which are the things of use from the perspective of
     412              :     practical computation. The point is that, for example, vector spaces and
     413              :     affine spaces admit different operations: whereas elements of a vector
     414              :     space can be added, the same is not true of the elements of the set
     415              :     underpinning an affine space. By introducing concepts for the abstract
     416              :     algebraic constructs, we can treat coordinates on all of these spaces in a
     417              :     common way by using constraints to enable or disable specific operations.
     418              :     Thus, the coordinates class template is templated on, amongst other things,
     419              :     a partial_m_torsor. To define such a space just requires introducing a
     420              :     struct exposing a small amount of data (types and values) known at compile
     421              :     time. These data determine whether we intend to model a vector space, a
     422              :     free module over a commutative ring, an affine space or whatever. This is
     423              :     sufficient for the coordinates implementation to expose the correct set of
     424              :     operations, giving a high degree of both type safety and expressivity.
     425              :  */

    1049              :       Understanding how to specify a basis requires some care. Consider first
    1050              :       the case of \f$ \bb{R}^d \f$, understood to be a vector space. (This

    1056              :       -# \f$ S \f$ is an index set of cardinality \f$ d \f$;

    1058              :          \f$ S \to \bb{R} \f$, equipped with pointwise addition and scalar

    1062              :       -# Take an element of \f$ \bb{R}^S \f$, \f$ v \f$ - a vector;
    1063              :       -# Take an element of \f$ S \f$, \f$ i \f$ - an index;

    1065              :          more natural): this returns the \f$ i \f$th coordinate, which in this
    1066              :          example is just a real number.

    1069              :       \f$ v(0) = 0.5 \f$ and \f$ v(1) = -0.5 \f$, which we might express as

    1071              :       suggest a paradox. We claimed in the introduction that the components of
    1072              :       a vector must be written with respect to a basis. And yet here we haven't
    1073              :       introduced a basis, just a function which in no way requires a basis for
